实现防抖搜索的三种方式

提示词 请展示在我们的 React 代码库中为任务筛选输入框实现防抖搜索的三种不同方式，并说明每种方案的取舍。

01内联 useEffect + setTimeout

防抖逻辑直接放在拥有该输入框的组件内部。

export function TaskSearch() {
  const [draft, setDraft] = useState('');
  const [query, setQuery] = useState('');

  useEffect(() => {
    const id = setTimeout(() => setQuery(draft), 300);
    return () => clearTimeout(id);
  }, [draft]);

  const { data } = useTasks({ search: query });

  return (
    <input
      value={draft}
      onChange={(e) => setDraft(e.target.value)}
      placeholder="Filter tasks…"
    />
  );
}
优点
缺点
无需学习新的抽象
每个搜索位置都会重复这段逻辑
方便在开发者工具中逐步调试
一个概念值却需要两份状态
不增加依赖，也不改变包体
延迟常量埋在组件主体里
包体影响： +0 kb 可测试性： 中 复用性： 低 SSR 安全： 是

02自定义 useDebounce Hook

把计时器提取到共享 Hook 中，放在 src/hooks/.

// src/hooks/useDebounce.ts
export function useDebounce<T>(value: T, ms = 300): T {
  const [debounced, setDebounced] = useState(value);
  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), ms);
    return () => clearTimeout(id);
  }, [value, ms]);
  return debounced;
}

// TaskSearch.tsx
const [draft, setDraft] = useState('');
const query = useDebounce(draft, 300);
const { data } = useTasks({ search: query });
优点
缺点
筛选器、命令栏、看板搜索都能复用同一个 import
多一个需要维护和记录的文件
用 fake timer 做单元测试非常简单
Generic T 会稍微弱化意图表达
延迟是可见且可调的参数
每次按键仍会重新渲染
包体影响： +0.2 kb 可测试性： 高 复用性： 高 SSR 安全： 是

03轻量外部库

采用 use-debounce 同时处理值和回调。

import { useDebouncedCallback }
  from 'use-debounce';

export function TaskSearch() {
  const [query, setQuery] = useState('');

  const onChange = useDebouncedCallback(
    (next: string) => setQuery(next),
    300,
    { leading: false, maxWait: 1000 },
  );

  const { data } = useTasks({ search: query });

  return (
    <input
      defaultValue=""
      onChange={(e) => onChange(e.target.value)}
    />
  );
}
优点
缺点
leading / trailing / maxWait 都由库替我们处理
增加需要审计和更新的运行时依赖
回调形式会跳过中间重新渲染
非受控输入偏离 Acme 表单模式
边界情况测试充分（卸载、flush、cancel）
为我们本可自维护的逻辑增加约 1.4 kb gzip
包体影响： +1.4 kb 可测试性： 高 复用性： 高 SSR 安全： 是

建议

Go with approach 02, the custom useDebounce hook。Acme 已经有三个地方手写了内联模式（任务筛选、命令面板、成员选择器），因此提取一个共享 Hook 可以去重，同时不引入新依赖。

只有当后续需要 maxWait or flush() 语义时再重新考虑方案 03 — 当需求超过十行 Hook 能覆盖的范围后，这个库的包体成本才值得。
