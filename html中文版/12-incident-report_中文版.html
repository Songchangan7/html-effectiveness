INC-2025-0412

任务同步 502 升高

SEV-2 已解决 持续时间 47 min 发现时间 4 月 12 日 · 14:07 负责人 Devon Park
摘要

一次配置发布将 sync-worker 层级的数据库连接池限制从 64 降到 8，导致正常下午负载下连接耗尽。同步 API 在 47 分钟内约 21% 请求返回 502。我们通过回滚配置并重启 worker 集群缓解；没有数据丢失。

时间线

14:02
配置变更 cfg-9a12 通过标准发布流水线提升到生产。
14:06
影响开始。 同步 worker 开始在连接池 checkout 上排队；p95 延迟超过 4 秒，负载均衡器开始返回 502。
14:07
告警触发： sync_5xx_rate > 2% 持续 60 秒。值班（Devon）确认。
14:18
初始假设是 API 服务部署有问题；回滚最近两次应用部署后没有效果。
14:31
Mira 加入并在 worker 仪表盘发现连接池等待饱和。调查从应用代码转向基础设施配置。
14:44
已缓解。 cfg-9a12 已回滚；worker 集群已重启。5xx 率在三分钟内降到 0.2% 以下。
14:49
监控保持绿色 5 分钟。事故宣布解决；状态页已更新。

根因

PR #4888 让连接池限制可按 worker 层级配置。新的 sync-worker key 本应继承全局值（64），但在本地测试时被硬编码为 8 并提交。配置 linter 只验证类型，不验证数值范围，因此变更通过了 CI。

由于配置发布和代码部署走不同流水线，值班的第一反应 — 回滚最近的应用部署 — 没有效果，并消耗了约 13 分钟诊断时间。

infra/config/workers.yaml
pool:
global_max_connections: 64
tiers:
- sync-worker: { max_connections: 64 }
+ sync-worker: { max_connections: 8 } # debug value, do not ship
webhook-worker: { max_connections: 32 }

影响

失败请求（502） ~41,200
峰值错误率 21.4%
受影响用户 ~2,300 workspaces
数据丢失 无 — 客户端已重试
SLA 违约 无（在月度预算内）
