摘要

通知发送原本内联发生在请求路径中。在负载下，它们会给 mutation 延迟增加 200–800 ms，并在 SMTP 池耗尽时静默丢弃邮件。这个 PR 将投递移到现有 pg-boss 队列上，让 API 立即返回，失败发送则按退避重试。

原因

上季度我们在评论中添加 @提及时，每次提及都会在保存评论的同一个事务里触发最多三次发送（站内、邮件、Slack）。上线时这没问题。但现在一次任务更新可能扇出到四十个关注者，这就不行了。

之前
  • 发送在 mutation handler 中内联运行
  • SMTP 超时 = comment
  • 没有重试 — 丢掉的邮件就没了
  • p99 on comments.create: 1.4 s
之后
  • handler 为每个收件人入队一个任务后返回
  • worker 使用指数退避重试 3 次
  • 重试耗尽后进入死信表供检查
  • p99 on comments.create: 180 ms （预发）

逐文件说明

按阅读顺序排列，而不是字母顺序。从 worker 开始 — 它是新东西 — 然后看入队调用点，再看管线接线。

这个 PR 的核心。 A pg-boss 订阅者，拉取 notify.deliver 任务，解析用户的渠道偏好，并调用正确的适配器。重试按渠道配置 — 邮件尝试三次，Slack 尝试一次，因为我们这边调用它的 API 已经是幂等的。

boss.work('notify.deliver', { batchSize: 20 }, async (jobs) => {
  for (const job of jobs) {
    const { userId, event, channel } = job.data;
    const prefs = await getPrefs(userId);
    if (!prefs[channel]) return;          // 用户静音了该渠道

    try {
      await adapters[channel].send(userId, event);
    } catch (err) {
      if (job.retryCount >= MAX_RETRY[channel]) {
        await deadLetter(job, err);         // 不要抛出 — ack 并停放
        return;
      }
      throw err;                            // pg-boss 重新调度
    }
  }
});
